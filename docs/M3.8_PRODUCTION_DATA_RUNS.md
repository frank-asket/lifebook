# M3.8 — Production data runs

Two one-time production changes from the launch plan (workstream 4). **Each needs the product owner's explicit approval before it runs.** Both are prepared, tested, and rehearsed; nothing has run on production.

Never paste a key, connection string, or reflection text in chat, tickets, or this file. The scripts print counts only.

---

## 1. Encrypt legacy reflections

**Why:** Daily Word and meditation reflections written before encryption shipped may still be stored as plain text. The API already reads both forms, so members notice nothing.

**What it does** (`apps/api/scripts/reflection-backfill.cjs`):
- **Dry run by default.** Without keys, it only counts plain-text and encrypted rows.
- **Before changing anything,** it decrypts every reflection the API has already encrypted. If even one won't open, the keys are wrong and it stops. On production it also refuses to run without at least one such reflection to check against, and refuses the staging keys outright.
- **Each row:** it encrypts with the same context the API uses, writes only if the row hasn't changed since it was read, reads it back, and decrypts it. If the round trip fails, it puts the original back and stops.
- **Afterwards** it rescans: `legacyAfter` and `unreadableAfter` must both be 0. Running it again changes nothing.

**Rehearsed on 18 October 2026** on a disposable PostgreSQL 17 with all migrations and 600 synthetic reflections (accents, emoji, newlines; a mix of plain and API-encrypted). 425 plain rows were encrypted in under 2 seconds with 0 conflicts, the rerun changed nothing, and an independent check decrypted all 600 back to their originals. Wrong keys were refused with nothing changed. The automated test (`test/reflection-backfill.test.cjs`) covers the same cases.

### Steps (operator machine, repo root)

1. **Build:** `pnpm --filter @lifebook/api build`
2. **Count (read-only):**
   ```bash
   node apps/api/scripts/reflection-backfill.cjs --target production --confirm-production <ref>
   ```
   If `meditations.legacy` and `dailyWord.legacy` are both 0, stop here: nothing needs encrypting. Tick the gate and record the counts.
3. **Back up** and **restore-test**, following runbook section A, steps 1–2.
4. **Load the production keys** into this shell from Render → `lifebook-api` → Environment (`REFLECTION_ENCRYPTION_KEYS`, `REFLECTION_ENCRYPTION_ACTIVE_KEY`). Don't write them to a file. Use `read -s` and `export`.
5. **Rehearse on the restored copy** (loopback only):
   ```bash
   DATABASE_URL=postgresql://…@127.0.0.1:<port>/<restore> node apps/api/scripts/reflection-backfill.cjs --target local
   DATABASE_URL=… node apps/api/scripts/reflection-backfill.cjs --target local --apply
   ```
   Expect `keyRing: "matches N existing encrypted reflections"`, then `legacyAfter: 0`, `unreadableAfter: 0`, `conflicts: 0`.
6. **Approval.** The product owner approves the production run, quoting the step 2 counts.
7. **Dry run on production with keys:** same as step 2. `keyRing` must say `matches …`, never `MISMATCH`.
8. **Apply:**
   ```bash
   node apps/api/scripts/reflection-backfill.cjs --target production --confirm-production <ref> --apply
   ```
9. **Verify:** `legacyAfter: 0`, `unreadableAfter: 0`, `conflicts: 0` for both, exit code 0. Have the dedicated test account open a past reflection in the app. Check the Render logs for errors.
10. **Clear the keys** from the shell (`unset REFLECTION_ENCRYPTION_KEYS REFLECTION_ENCRYPTION_ACTIVE_KEY`) and record the counts, date and approver below.

**If `--no-existing-ciphertext` seems necessary** (production has no encrypted reflection to compare against): don't use it on your own. First write a reflection with the test account through the production app, which creates one, then repeat step 7.

**Rollback:** the backup from step 3. Never remove a key from `REFLECTION_ENCRYPTION_KEYS` while any row or backup uses it.

## 2. Daily care-data purge

**Why:** the privacy notice promises pastoral care conversations are deleted 90 days after a request closes, and resolved safety reports after 365 days. Requests no pastor takes within 30 days are closed so they enter the same cycle.

**What it does:** the API now carries the schedule itself (`CarePurgeScheduler` in `apps/api/src/care`). With `CARE_PURGE_SCHEDULE=on` it runs one pass a minute after start, then every 6 hours. Each pass takes a database advisory lock, so only one instance purges at a time. It logs counts only. A failed pass is logged by error type and retried at the next run. Passes are idempotent, so restarts and deploys only make it run sooner. **It is off until the variable is set,** so merging this code changes nothing.

No new service, cron job, or secret is needed, which keeps it free on Render.

### Steps

1. **Preview (read-only):** `node apps/api/scripts/care-purge.cjs --target production --confirm-production <ref>` shows what the first pass will do.
2. **Approval.** The product owner approves switching it on.
3. **Switch on:** Render → `lifebook-api` → Environment → add `CARE_PURGE_SCHEDULE` = `on` → Save (Render restarts the service).
4. **Verify:** about a minute later, the Render logs show `[CarePurge] Retention applied: …` with counts. Run step 1 again; every count should now be 0.
5. **Switch off** at any time by removing the variable.
